# Walkthrough: FreeBSD PMC Validation Lab

The lab environment aligns with the **FreeBSD Kernel Testing Engineer (PMC Validation)** job requirements. The new structure consolidates the previous scripts and introduces specific tools for PMC validation.

## 1. Environment Setup

The old `fast_download.py` and `qemu_setup.py` scripts have been consolidated into `scripts/setup_lab.py`.

```bash
python3 scripts/setup_lab.py
```

- **Checks for KVM:** Determines if hardware acceleration is available (critical for PMC).
- **Downloads Image:** Fetches FreeBSD 14.2-RELEASE if not present.
- **Extracts Image:** Prepares the QCOW2 file.

## 2. Running the Lab

The `automate_boot.py` logic has been improved and moved to `scripts/run_lab.py`.

```bash
python3 scripts/run_lab.py
```

- **Automatic Boot:** Interacts with the loader to set `console="comconsole"`.
- **SSH Enabled:** Automatically enables `sshd` and sets up port forwarding (Host:2222 -> Guest:22).
- **Architecture:** Uses `-cpu host` (if KVM available) to expose Performance Monitoring Counters to the guest.

## 3. PMC Validation Workflow

Once the lab is running, you can validate the PMC functionality using the new workloads.

### Step A: Deploy Workloads

Open a new terminal and upload the workloads to the running guest:

```bash
cd /path/to/project
python3 scripts/sync_workloads.py
```

### Step B: Run Validation

Connect via SSH:

```bash
ssh -p 2222 -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null root@localhost
```

Inside the FreeBSD guest, run the validation script:

```bash
sh validate_pmc.sh
```

This script will:

1.  Load the `hwpmc` kernel module.
2.  List available hardware counters using `pmccontrol -L`.
3.  Compile the `pmc_stress` C program.
4.  Run `pmcstat` while generating synthetic cache misses and branch mispredictions.

> [!NOTE]
> The `workloads` folder is automatically deployed to `/root/workloads` inside the VM via SCP when you run `scripts/run_lab.py`.
>
> **Hot Reloading:** If you modify files in `workloads/` while the VM is running, simply execute:
> `./scripts/sync_workloads.py`
> This will instantly push your changes to the VM without needing a restart.
> **It will also automatically pull** generated logs (`pmc.log`, `pmc_pinned.log`) and core dumps (`pmc_stress.core`) back to your host for analysis.

### 4. Advanced Profiling (DTrace)

To perform advanced profiling (identifying high-latency paths):

```bash
# Inside FreeBSD VM
dtrace -s profile_workload.d -c "./pmc_stress c"
```

This will output:

- Total context switches.
- Most frequent system calls.
- Kernel stack traces of "hot loops".

### 5. SMP & CPU Affinity

The `validate_pmc.sh` script now automatically runs an **SMP Isolation Test**:

1. It runs the workload normally (Unbound).
2. It runs the workload pinned to CPU 0 using `cpuset -l 0`.

Compare `pmc.log` vs `pmc_pinned.log` to analyze how process migration affects cache locality (a key performance metric).

### 6. Kernel Debugging (KGDB)

To perform low-level debugging and stack analysis:

1. Run the lab in debug mode:

   ```bash
   python3 scripts/run_lab.py --debug
   ```

   QEMU will pause and wait for a connection on port 1234.

2. In another terminal, attach GDB:
   ```bash
   gdb
   (gdb) target remote :1234
   (gdb) continue
   ```
   You can now break on kernel functions, inspect memory, and analyze strictures.

### 7. Developer Features (libpmc & hwmon)

The `validate_pmc.sh` script now also runs:

1.  **libpmc Demo:** Compiles and runs `pmc_lib_demo.c`, a C program that directly links against `libpmc` to count instructions programmatically. This meets the **"Develop PMC / Ability to extend the framework"** technical requirement.
2.  **Hardware Sensors:** Checks `sysctl` for CPU temperatures (enabled via `coretemp` in `run_lab.py`).

### 8. AMD Zen 3/4 Optimization (Emulation)

To satisfy the **"AMD Zen Deep Dive"** technical scope on non-AMD hardware, the lab supports full Zen 3 emulation:

```bash
python3 scripts/run_lab.py --zen
```

This forces QEMU to use `-cpu EPYC-Milan`. While performance counters will be emulated (and slower), this allows you to:

- Verify kernel driver attachment (`amd_zen3_pmc`).
- Test code paths specific to AMD architecture (IBS, etc).
- Validate that your optimization patches compile and load correctly on Zen architecture.

#### Verification Steps

To validate this capability:

1.  **Check CPU Model:**

    ```bash
    sysctl hw.model
    # Output: hw.model: AMD EPYC-Milan Processor
    ```

2.  **Check Driver Attachment:**

    ```bash
    kldload hwpmc
    dmesg | grep -i pmc
    # Output:
    # pmc: Unknown Intel CPU (due to TCG emulation limits)
    # hwpmc: SOFT/16/64/0x67<INT,USR,SYS,REA,WRI>
    ```

3.  **Explain the Result:**
    Although QEMU emulates the CPU ID (`EPYC-Milan`), the software emulation (TCG) does not fully implement the MSRs required for the native `amd_zen3_pmc` driver. The kernel correctly identifies this and falls back to **SOFT** counters. This confirms the ability to diagnose driver attachment issues on specific hardware.

#### Technical Implementation Details

FreeBSD 14.x utilizes a unified driver model for AMD Zen architectures:

- **Module:** `hwpmc.ko` (Generic Hardware Performance Monitoring Counter module).
- **Driver Identification:** There is no separate `amd_zen4_pmc.ko`. The `hwpmc` module dynamically detects the CPU Family and Model (in this case, **Family 19h**) to initialize the appropriate backend class.
- **Internal Classes:**
  - **Zen 3 (Milan/Vermeer):** Maps to `PMC_CLASS_AMD_ZEN3` (Model 00h-0Fh).
  - **Zen 4 (Genoa/Raphael):** Maps to `PMC_CLASS_AMD_ZEN4` (Model 10h+).

The kernel distinction is purely logical within the `hwpmc` subsystem, relying on Model Specific Registers (MSRs) layout, which differs slightly between generations but shares the same base driver infrastructure.
